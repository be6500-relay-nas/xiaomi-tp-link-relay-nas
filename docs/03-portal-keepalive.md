# 03 · Portal 认证保活

校园 Web 认证（Portal）的会话有有效期、会掉线、断电后要重登。目标：**全自动，无感知**。

## 通用流程

Portal 厂商五花八门（Dr.COM、深澜 srun 等），共同点：

1. 未认证时，任意 HTTP 请求被 302 到认证页（或 DNS 劫持）
2. POST 账号密码（密码通常有前端加盐算法，抓包/读 JS 可得）
3. 认证成功拿到会话；之后靠周期性心跳维持
4. 掉线检测：`curl -m 6 http://<generate_204 地址>` 非 204 即认为掉线

> 具体厂商的认证报文网上资料很多，此处不展开；把"认证"抽象成一个 `auth_run.sh` 脚本，失败非 0 退出。

## 自愈体系（三层兜底）

```
每分钟 keeper（crontab）
  ├─ 外网 204 探测失败 → 重跑 auth_run.sh
  ├─ 中继接口无 IP → 重新拉起 STA（注意：用 ubus 重连，别 ifup wwan —— 本固件 ifup 会重建整个无线，AP 一起闪断）
  └─ mihomo/dropbear/工作台进程不在 → 拉起

开机 fastboot.sh（rc.local 后台拉起）
  └─ 自适应等默认路由就绪（替代固定 sleep 20）→ 180s 窗口内每 8s 跑一次 keepalive，通了立刻退出

认证侧指数退避
  └─ 连续失败 30→60→120→300→600s，防止风暴
```

> 💡 "重启后连上网太慢"的根因往往不是固件启动慢，而是**第一次尝试失败后要等分钟级兜底**。
> 把"等下一轮"换成"高频多试几次"（同时清掉 keeper 的节流时间戳与退避文件），开机到出网可以从 5 分钟压到 40 秒。

## 关键经验

- **掉线判定要用"日志节奏"而不是时间戳**：路由器时钟可能漂移过又被 NTP 校正，旧日志的时间戳会"看着很新"。
  环形日志（上限 N 条）判断是否仍在掉线：最新条目**内容**是否还在变（约 6 分钟一条），不变即已自愈
- **时钟漂移单独修**：`date +%s` 与 PC epoch 对比是唯一可靠判据；`date -s @<epoch>` 秒修
- 🔴 **局域网里任何设备直连校园 WiFi 并完成认证，都可能占掉名额或顶掉路由器的会话**——
  keeper 日志里"中继无 IP→重连"风暴的常见真凶是室友的电脑。诊断第一步先看接入设备表
- keeper 的每个动作加**冷却时间**（如 120s），避免故障时自杀式循环重启
